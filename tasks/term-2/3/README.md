# Отчет о нагрузочном тестировании

## Сборка и запуск

### 1. Собрать jar из lab-1 (JSON-парсер)

```
javac --release 21 -d out json\*.java
jar cf lab1-json.jar -C out .
```

### 2. Собрать jar из lab-2 (HTTP-сервер)

```
javac --release 21 -d out src\main\java\httpserver\HttpMethod.java src\main\java\httpserver\HttpRequest.java src\main\java\httpserver\HttpRequestParser.java src\main\java\httpserver\HttpResponse.java src\main\java\httpserver\HttpServer.java src\main\java\httpserver\RouteKey.java
jar cf lab2-httpserver.jar -C out .
```

Оба jar помещаются в папку libs.

### 3. Запустить тест

```
gradlew.bat run
```

Программа последовательно запускает все четыре конфигурации, проводит замеры, затем выводит итоговую таблицу. База данных SQLite создаётся автоматически в папке `data/`.

---

## Описание эксперимента

Тестируется HTTP-сервер из lab-2 в четырёх конфигурациях — комбинации двух типов потоков и двух JSON-библиотек:

| Конфигурация | Тип потоков | JSON-библиотека |
|---|---|---|
| Virtual + Own JSON | Virtual Threads (Java 21) | Собственный парсер (lab-1) |
| Virtual + Gson | Virtual Threads (Java 21) | Gson 2.10 |
| Classic + Own JSON | Фиксированный пул, 8 потоков | Собственный парсер (lab-1) |
| Classic + Gson | Фиксированный пул, 8 потоков | Gson 2.10 |

Для каждой конфигурации сервер запускается заново на порту 9090, измеряется среднее время ответа на двух эндпоинтах.

**POST /request1** — I/O-нагрузка:
1. Принимает JSON: `{"value": "hello from load tester"}`
2. Парсит JSON и извлекает поле `value`
3. Записывает значение в базу данных SQLite (INSERT)
4. Читает запись обратно по сгенерированному id (SELECT)
5. Возвращает прочитанную строку

**POST /request2** — CPU-нагрузка:
1. Принимает JSON: `{"n": 30}`
2. Парсит JSON и извлекает поле `n`
3. Вычисляет Fibonacci(30) итеративно
4. Возвращает JSON: `{"n": 30, "result": 832040}`

SQLite настроен с `PRAGMA journal_mode=WAL` и `PRAGMA busy_timeout=5000`.

Клиент и сервер запускались на одной машине.

## Результаты

| Запрос | Virtual + Own JSON | Virtual + Gson | Classic + Own JSON | Classic + Gson |
|---|---|---|---|---|
| Request-1 (I/O, SQLite) | 264 мс | 398 мс | 254 мс | 235 мс |
| Request-2 (CPU, Fibonacci) | 55 мс | 29 мс | 27 мс | 30 мс |

Показано среднее время на один запрос в миллисекундах.


## Анализ результатов

Request-1 (I/O-bound, SQLite):
Основное время тратится на запись и чтение из базы данных. Все четыре конфигурации показали близкие результаты (235–398 мс). Конфигурация Virtual + Gson оказалась медленнее остальных из-за накладных расходов планировщика виртуальных потоков при активном ожидании на I/O в связке с более тяжёлым парсингом Gson.

Request-2 (CPU-bound, Fibonacci):
Fibonacci(30) вычисляется очень быстро, поэтому время ответа определяется в основном парсингом JSON и накладными расходами сети. Классические потоки показали результат немного лучше виртуальных. Собственный парсер на виртуальных потоках показал наихудший результат (55 мс), так как парсер не является потокобезопасным при высокой конкурентности, что приводит к редким ошибкам и дополнительным задержкам.

Вывод:
Виртуальные потоки эффективнее классических при долгом ожидании I/O, однако при быстрой локальной SQLite разница нивелируется. Gson в целом стабильнее собственного парсера при параллельной нагрузке.
