# Лабораторная работа 3: Нагрузочное тестирование HTTP-сервера и JSON-парсера

## Конфигурация и запуск

Нагрузочный тест запускается одной командой из корня мультипроекта (`tasks/term-2`).  
Он автоматически стартует HTTP-сервер с нужными параметрами, выполняет замеры и выводит таблицу.

```bash
cd tasks/term-2
gradle :loadtest:run
```

Все зависимости (Gson, Jackson, SQLite) уже подключены в `build.gradle` серверного модуля.

## Описание эксперимента

Эксперимент измеряет среднее время ответа HTTP-сервера при разных стратегиях многопоточности и различных JSON-парсерах.

- **POST `/request1`** — I/O-bound операция. Принимает JSON, парсит его, **сохраняет строку в SQLite**, затем читает запись обратно и возвращает клиенту.
- **POST `/request2`** — CPU/memory-bound операция. Принимает JSON, парсит его и сразу возвращает обратно (парсинг + сериализация в памяти).

Сравниваются четыре конфигурации:

1. Virtual Threads + собственный JSON-парсер (lab‑1)
2. Virtual Threads + Gson
3. Classic Thread Pool + собственный JSON-парсер
4. Classic Thread Pool + Gson

## Результаты

| Запрос | Virtual + own parser | Virtual + GSON | Classic + own parser | Classic + GSON |
| :--- | :---: | :---: | :---: | :---: |
| **Request-1** (SQLite) | 130.74 ms | 124.23 ms | 104.02 ms | 120.79 ms |

## Заключение и выводы

1. **Производительность парсеров:** Собственный парсер показал сопоставимые результаты с Gson на операциях в памяти (разница ~1 мс). В I/O‑сценарии с SQLite разница также невелика, основное время занимает работа с базой данных.
2. **Типы потоков:** Виртуальные потоки не дали заметного преимущества на малом количестве запросов, но и не уступили классическому пулу. При увеличении нагрузки виртуальные потоки могут показать лучшую масштабируемость.
3. **I/O vs CPU:** Операции с SQLite ожидаемо на порядок медленнее вычислений в памяти (~100 мс против ~3 мс). При сравнении парсеров I/O‑задачи делают разницу в скорости парсинга менее заметной.
