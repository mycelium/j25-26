# Load testing report

## 1. Настройка и запуск

### Требования

- Java 21+ (для поддержки виртуальных потоков)
- Установленная библиотека Gson (файл `gson-2.10.1.jar` в папке `lib`)

### Сборка и запуск

1. Открыть проект в корневой папке `3`.

2. В файле `src/PerformanceServer.java` настроить нужный режим:
   - `USE_GSON` — использовать Gson (`true`) или собственную библиотеку (`false`)
   - `USE_VIRTUAL_THREADS` — использовать виртуальные потоки (`true`) или классический пул (`false`)
   - При необходимости изменить количество потоков классического пула `THREAD_POOL_SIZE`

3. В файле `src/LoadTest.java` настроить параметры нагрузки:
   - `REQUESTS` — общее количество запросов на каждый endpoint
   - `CONCURRENCY` — количество параллельных клиентов
   - `LABEL` — метка конфигурации, отображается в CSV (например `"Virtual+GSON"`)

4. В командной строке перейти в корень проекта:
   ```bash
   cd tasks\term-2\3
   ```

5. Компиляция сервера и тестового клиента:
   ```bash
   javac -cp "lib/*" src/PerformanceServer.java src/LoadTest.java
   ```

6. Запуск сервера (должен быть запущен **до** теста):
   ```bash
   java -cp "lib/*;src" PerformanceServer
   ```
   > Для изменения параметров сервера отредактируйте константы `USE_VIRTUAL_THREADS`, `USE_GSON`, `THREAD_POOL_SIZE` в `src/PerformanceServer.java`.

7. Во время работы сервера запустить нагрузочный тест:
   ```bash
   java -cp "lib/*;src" LoadTest
   ```
   > Результаты автоматически сохраняются в `results.csv`.

8. Повторить шаги 2–7 для каждой из четырёх конфигураций:

   | Запуск | `USE_VIRTUAL_THREADS` | `USE_GSON` | `LABEL`              |
   |--------|-----------------------|------------|----------------------|
   | 1      | `true`                | `false`    | `Virtual+OwnParser`  |
   | 2      | `true`                | `true`     | `Virtual+GSON`       |
   | 3      | `false`               | `false`    | `Classic+OwnParser`  |
   | 4      | `false`               | `true`     | `Classic+GSON`       |

## 2. Описание эксперимента

Эксперимент измеряет среднее время обработки двух типов HTTP-запросов:

- **Request-1**: сервер принимает JSON `{"data":"..."}`, парсит его, сохраняет строку в файл `storage.txt`, затем читает её обратно и возвращает JSON `{"stored":"...","retrieved":"..."}`.
- **Request-2**: сервер принимает JSON `{"a":...,"b":...}`, парсит его, вычисляет сумму `a + b` в памяти и возвращает JSON `{"result":...}`.

Сравниваются четыре конфигурации:

- Собственный JSON-парсер (из лабораторной №1) + виртуальные потоки
- Собственный JSON-парсер + классический пул потоков
- Gson + виртуальные потоки
- Gson + классический пул потоков

- **Количество параллельных клиентов (`CONCURRENCY`)**: 50
- **Общее количество запросов на каждый endpoint (`REQUESTS`)**: 100

- **Тело запроса Request-1**: `{"data":"test data"}` (~25 байт)

## 6. Анализ результатов

**Виртуальные vs классические потоки.**
Для Request-2 (вычисления в памяти) виртуальные потоки заметно быстрее: 6–7 мс против 10–11 мс у классического пула. Это объясняется накладными расходами на ожидание в очереди — при 50 параллельных клиентах и пуле из 16 потоков классический вариант вынужден ставить запросы в очередь. Виртуальные потоки создаются под каждый запрос без ограничений, поэтому очереди не возникает.

Для Request-1 (файловый I/O) картина обратная: классические потоки показали чуть лучшее время. Причина — в коде используется `synchronized` блок при записи и чтении файла, из-за чего все потоки всё равно выстраиваются в очередь у одного замка. В таких условиях преимущество виртуальных потоков нивелируется, а небольшой overhead на их создание даёт незначительный проигрыш.

**Собственный парсер vs Gson.**
Для Request-2 собственный парсер стабильно быстрее: 6,49 мс против 7,43 мс (virtual) и 10,15 мс против 10,62 мс (classic). Собственный парсер из lab-1 напрямую строит `Map<String, Object>` без рефлексии, тогда как Gson выполняет дополнительную работу по определению типов. Для Request-1 разница незначительна, так как доминирует время файловых операций.

**Request-1 vs Request-2.**
Request-1 примерно в 80–130 раз медленнее Request-2. Узкое место — синхронизированные запись и чтение файла `storage.txt`: при каждом запросе файл открывается, дописывается строка, затем читается целиком. Это блокирующие I/O операции, которые при высокой нагрузке становятся главным bottleneck'ом независимо от типа потоков и парсера.
