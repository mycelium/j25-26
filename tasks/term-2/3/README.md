# Load Testing Report

## Настройка и запуск

### Требования

- Java 21+
- Gradle (или использовать `./gradlew`)

### Сборка

```bash
./gradlew serverJar testerJar
```
или

```bash
gradle serverJar testerJar
```

После сборки в `build/libs/` появятся два jar-файла:
- `server.jar` — HTTP-сервер
- `tester.jar` — нагрузочный тестировщик

### Запуск сервера

```bash
java -jar build/libs/server.jar <port> <virtual|classic> <own|gson>
```

Параметры:
- `port` — порт сервера (например, `8080`)
- `virtual|classic` — тип потоков: виртуальные или классические
- `own|gson` — JSON-парсер: собственный (lab-1) или Gson

Пример:
```bash
java -jar build/libs/server.jar 8080 virtual own
```

### Запуск нагрузочного теста

В отдельном терминале (или на другой машине):

```bash
java -jar build/libs/tester.jar <host> <port>
```

Пример:
```bash
java -jar build/libs/tester.jar http://localhost 8080
```

Для воспроизведения всех 4 конфигураций из таблицы — запускать сервер поочерёдно с разными аргументами, каждый раз прогоняя тестировщик:

```bash
java -jar build/libs/server.jar 8080 virtual own
java -jar build/libs/server.jar 8080 virtual gson
java -jar build/libs/server.jar 8080 classic own
java -jar build/libs/server.jar 8080 classic gson
```

## Описание эксперимента

Сравниваются 4 конфигурации сервера:

1. Виртуальные потоки + собственный парсер (lab-1)
2. Виртуальные потоки + Gson
3. Классические потоки + собственный парсер (lab-1)
4. Классические потоки + Gson

Для каждой конфигурации измеряется среднее время обработки двух типов запросов:

**Request-1 (I/O-bound):**
Сервер принимает `{"data": "<строка ~512 байт>"}`, парсит JSON, записывает `data` в SQLite,
читает последнюю запись из БД и возвращает `{"stored": "...", "retrieved": "..."}`.
Основное время уходит на дисковый I/O (запись + чтение SQLite).

**Request-2 (CPU/memory-bound):**
Сервер принимает `{"a": 10000}`, парсит JSON, вычисляет сумму квадратов от 1 до `a`
с кэшированием результата в `ConcurrentHashMap` и возвращает `{"result": ...}`.
После первого запроса результат берётся из кэша, поэтому основное время — парсинг и сериализация JSON.

## Анализ результатов

**Request-1 (I/O-bound):**
Виртуальные потоки показывают заметное преимущество (~12–43% быстрее) по сравнению с классическими.
Это ожидаемо: при ожидании диска (SQLite) виртуальный поток освобождает carrier thread, позволяя
обрабатывать другие запросы. Классические потоки блокируются целиком на I/O.
Разница между собственным парсером и Gson в этой конфигурации невелика, так как узким местом
является диск, а не парсинг.

**Request-2 (CPU/memory-bound):**
Разница между виртуальными и классическими потоками здесь минимальна — после прогрева результат
вычисления берётся из кэша и операция почти полностью CPU-bound без блокирующих вызовов.
Собственный парсер незначительно быстрее Gson на простых структурах (`{"a": 10000}`),
что объясняется меньшими накладными расходами при отсутствии reflection.

**Общий вывод:**
Виртуальные потоки дают наибольший выигрыш при I/O-нагрузке. Для CPU-bound задач разница
между типами потоков несущественна. Собственный парсер сопоставим с Gson по скорости
на простых структурах.
