### 3. Load testing report

## Компиляция 
  1. В командной строке перейти в корневую папку проекта  ...\term-2\3.
  2. В данной папке выполнить через терминал команду javac -cp "lib/*" -d out src/loadtest/LoadTestClient.java src/loadtest/LoadTestRunner.java

## Запуск
### Настраиваемые параметры запуска 
  1.  --port <порт> - порт, на котором будет запущен HTTP-сервер во время тестирования. По умолчанию: 8085
  2.  --server-threads <число> -  размер пула потоков для классической (не‑виртуальной) модели обработки запросов. По умолчанию: 10
  3.  --warmup-requests <число> - количество запросов, отправляемых после прогрева JIT, но перед основным замером для каждой конфигурации. По умолчанию: 1000
  4.  --warmup-concurrency <число> - количество одновременных запросов во время прогревочной фазы. По умолчанию: 50
  5.  --test-requests <число> - бщее количество запросов, отправляемых на каждый endpoint во время основного измерения для одной конфигурации. По умолчанию 5000
  6.  --test-concurrency <число> - количество одновременно работающих клиентских потоков во время основного замера. По умолчанию: 500


### Запуск с параметрами по умолчанию 
  1. В командной строке перейти в корневую папку проекта  ...\term-2\3 .
  2. В данной папке выполнить через терминал команду java -cp "out;lib/*" loadtest.LoadTestRunner


### Запуск с измененными параметрами  
  1. В командной строке перейти в корневую папку проекта  ...\term-2\3 .
  2. В данной папке выполнить через терминал команду с измененными парамтерами. Например: java -cp "lib/*;." loadtest.LoadTestRunner --test-requests 2000 --test-concurrency 80

## Описание эксперимента
Эксперимент сравнивает четыре конфигурации сервера:

1. Собственный JSON‑парсер + виртуальные потоки

2. Gson + виртуальные потоки

3. Собственный JSON‑парсер + классический пул потоков (фиксированный размер)

4. Gson + классический пул потоков

Сервер обрабатывает два типа POST‑запросов:

1. /request1 (IO‑bound):
Принимает JSON вида {"value": "..."}. Сохраняет строку во временный файл в папке storage/, затем считывает её обратно и возвращает JSON {"retrieved": "..."}. Операция включает запись и чтение диска.

2. /request2 (CPU‑bound):
Принимает JSON вида {"n": число}. Вычисляет n-е число Фибоначчи (итеративный алгоритм) и возвращает JSON {"n": ..., "result": ...}.

Каждая конфигурация тестируется в изолированном запуске: сервер стартует, выполняются прогревочные запросы, затем основной замер с параметрами: totalRequests = 10000, concurrency = 1000.
Результатом является среднее арифметическое время успешного запроса для каждого endpoint.
## Характеристики аппаратного обеспечения
1. Операционная система: Windows 11
2. Процессор: 13th Gen Intel(R) Core(TM) i5-13420H 2.10 GHz
3. Оперативная память: 16 Гб
4. Дисковое пространство: 477 Gb

## Параметры эксперимента
1. Общее количество запросов на один endpoint (TEST_REQUESTS): 5000
2. Параллелизм (одновременных клиентов) (TEST_CONCURRENCY): 500
3. Размер классического пула потоков сервера (SERVER_THREADS_CLASSIC): 10
4. Прогрев:
     JVM‑прогрев: 2000 запросов с параллелизмом 20 на каждый endpoint
     Warm‑up: 1000 запросов с параллелизмом 50
5. Тело запроса Request‑1 ~40 байт
6. Тело запроса Request‑2 ~12 байт
